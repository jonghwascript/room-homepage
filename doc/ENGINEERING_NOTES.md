# Engineering Notes

이 문서는 개발 대화에서 확인한 구현 결정과 문제 해결 과정을 기록한다. 현재 소스와 과거 검증 결과를 구분하며, 전체 요구사항이나 접근성 준수를 보장하는 문서는 아니다.

## 1. 메뉴를 닫은 후 섹션으로 이동

관련 파일: [메뉴 스크립트](../src/js/components/nav-panel.js), [메뉴 스타일](../src/scss/components/_nav-panel.scss), [페이지 스타일](../src/scss/pages/_home.scss).

- 같은 페이지의 유효한 대상 링크를 클릭하면 기본 앵커 이동을 막고 패널부터 닫는다.
- 패널 내부 요소의 `transform` 전환이 끝나는 `transitionend` 시점에 대상 섹션으로 스크롤한다. 현재 패널 전환 시간은 0.3초다.
- 전환 이벤트가 발생하지 않을 때를 대비해 computed style의 전환 시간·지연을 읽고 여유 50ms를 더한 타이머를 사용한다.
- 대상에 포커스를 옮길 때는 `preventScroll: true`를 사용하고, 실제 이동은 `scrollIntoView()`로 처리한다.
- 링크의 해시와 대상 ID가 일치해야 한다. 예를 들어 `href="#about"`은 `id="about"`으로 연결하며 ID는 문서 안에서 고유해야 한다.
- 대상이 없거나 다른 페이지로 이동하는 링크는 기존 브라우저 이동을 유지한다. 수정 키 클릭, 다운로드, 새 창 링크는 가로채지 않는다.
- 동작 줄이기 설정에서는 패널 전환과 부드러운 스크롤을 생략한다.

## 2. 사진과 상품 설명의 전환

관련 파일: [main.js](../src/js/main.js), [index.html](../src/pages/index.html).

사진 이동은 Splide, 설명 전환은 Web Animations API가 담당한다. CSS `@keyframes`를 별도로 연결할 필요는 없다.

| 대상 | 현재 설정 |
| --- | --- |
| 사진 | `type: 'loop'`, 500ms |
| 사진 easing | `cubic-bezier(0.42, 0, 0.58, 1)` |
| 기존 설명 퇴장 | 투명도 1 → 0, 120ms, `ease-in` |
| 새 설명 등장 | 투명도 0 → 1, 아래 8px → 원위치, 300ms, `ease-out` |

사진과 설명 전환은 `move` 이벤트에서 함께 시작한다. 설명은 기존 내용 퇴장 후 새 내용이 등장하므로 약 420ms, 사진은 500ms에 완료된다. 두 전환의 완료 시점을 가깝게 맞추기 위한 선택이며, 자연스러움에 대한 최종 판단은 실제 화면에서 한다.

- `mounted` 이벤트에서는 첫 설명을 애니메이션 없이 맞춘다. 이벤트를 먼저 등록한 뒤 `splide.mount()`를 호출해야 초기 이벤트를 놓치지 않는다.
- 0부터 시작하는 슬라이드 인덱스를 `slide01`, `slide02`, `slide03` 클래스와 연결한다.
- `u-hidden`은 `display: none !important`이므로 퇴장 전에 붙이면 효과가 보이지 않는다. 퇴장 완료를 기다린 뒤 클래스를 교체한다.
- 빠른 연속 전환에서는 진행 중 애니메이션을 취소하고, `transitionId`로 이전 비동기 작업이 최신 설명을 덮어쓰지 못하게 한다.
- 취소된 애니메이션의 `finished` Promise도 처리할 수 있도록 `Promise.allSettled()`를 사용한다.
- 기울기는 동작 확인용 실험이었다. 최종 코드에는 회전 효과가 없다.
- `type: 'fade'`는 검토한 대안일 뿐 현재 적용값은 아니다.

## 3. 애니메이션이 보이지 않았던 원인

사용자 브라우저에서 아래 결과가 `true`인 것을 확인했다.

```js
matchMedia('(prefers-reduced-motion: reduce)').matches
```

현재 코드는 `immediate || reducedMotion.matches`가 참이면 설명 애니메이션을 생략한다. 따라서 소스가 반영되어 있어도 시스템이나 브라우저가 동작 줄이기를 요청하면 설명만 즉시 교체된다.

확인 절차:

1. 위 미디어 쿼리 값을 확인한다.
2. Windows 11에서는 **설정 → 접근성 → 시각 효과 → 애니메이션 효과**를 확인한다. 애니메이션을 보려면 이 항목을 켠다.
3. Chrome 개발자 도구의 Rendering 패널에서 `prefers-reduced-motion` 에뮬레이션을 확인한다. `No emulation`은 시스템 설정을 따르며, 시스템 자체가 reduce이면 여전히 참일 수 있다.
4. 새로고침 후 실제 로드된 JavaScript와 현재 소스가 같은지 확인한다.

사용자 설정을 무시하는 코드를 최종 구현으로 남기지 않는다. 또한 투명도 0에서 시작하는 작은 움직임은 눈에 잘 띄지 않을 수 있다. 애니메이션 중간을 일시 정지한 캡처는 순간 상태를 보여줄 뿐, 실제 재생에서 효과가 잘 보인다는 근거는 아니다.

## 4. 이미지 비율과 l-frame

관련 파일: [공통 레이아웃](../src/scss/layout/_every-layout.scss), [슬라이더 스타일](../src/scss/components/_splide.scss).

- `--n`은 가로, `--d`는 세로의 비율값이다. 원본 크기를 단위 없이 넣어도 되지만 실제 px 크기를 고정하지는 않는다.
- 기준은 원하는 표시 비율이다. 현재 슬라이더 프레임은 기본 `376 / 360`, 태블릿 `768 / 400`, 데스크톱 `840 / 534`이며 공통 기본값은 `16 / 9`다.
- 공통 클래스가 변수 기본값을 직접 선언하므로, 비율을 바꿀 때는 부모에서 상속시키기보다 `l-frame`이 붙은 요소에 지정하고 캐스케이드 순서도 확인한다.
- 프레임 너비가 커지면 같은 비율로 높이도 커진다. 큰 화면에서 높이가 과도하다면 레이아웃 너비나 표시 비율을 별도로 설계해야 한다.
- `l-frame > img` 규칙을 적용하려고 `<picture class="splide__picture l-frame">` 구조를 사용한다. 프레임을 `<li>`에 붙이면 중간의 `picture` 때문에 직접 자식 선택자가 이미지에 닿지 않는다.
- `object-fit: cover`는 표시 비율과 원본 비율이 다르면 사진 일부를 자른다.
- 모바일·데스크톱 이미지 전환과 프레임 비율 전환은 별개다. `source`가 바뀐다고 CSS의 비율까지 자동으로 바뀌지는 않는다.

## 5. SVG 화살표 크기

관련 파일: [페이지 마크업](../src/pages/index.html), [페이지 스타일](../src/scss/pages/_home.scss).

`viewBox="0 0 40 12"`인 SVG에서 기본 비율 유지 동작을 사용하는 경우, 너비를 54px로 늘려도 높이를 12px로 고정하면 그림은 그대로이고 좌우 여백이 생길 수 있다.

- 비례 확대하려면 너비와 함께 높이도 조정한다.
- 높이는 고정하고 가로만 늘리려면 `preserveAspectRatio="none"`을 사용한다. 이 경우 그림 자체가 가로로 늘어난다.
- 현재 마크업에는 `preserveAspectRatio="none"`, 스타일에는 너비 54px·높이 auto가 설정되어 있다. 높이 고정 방식과 동일하다고 간주하지 않는다.

## 6. 사진이 비치는 비네팅

관련 파일: [슬라이더 스타일](../src/scss/components/_splide.scss).

기존 가상 요소의 불투명한 `#989898` 배경이 사진을 덮었다. 이를 제거하고 투명한 방사형 그라데이션으로 바꿨다.

```scss
background: radial-gradient(
  ellipse at center,
  transparent 45%,
  rgba(0, 0, 0, 0.18) 100%
);
```

중앙은 투명하고 가장자리만 최대 18% 검정으로 덮는다. `pointer-events: none`으로 사진 위의 가상 요소가 포인터 입력을 가로채지 않게 한다.

- 이번 문서 작성에서는 현재 소스와 경로를 대조했으며 브라우저 검사를 다시 수행하지 않았다.

## 8. 빌드와 Git 작업 메모

- `dist`는 직접 수정하거나 삭제하지 않는다. 현재 `npm run build`와 `npm run dev`에는 dist 삭제가 포함되므로 실행하지 않는다.
- 출력 파일 없이 확인할 때 사용한 명령:

```sh
node --check src/js/main.js
node --check src/js/components/nav-panel.js
node -e "require('sass').compile('src/scss/style.scss')"
git diff --check
git diff --cached --check
```

- 같은 파일에 섞인 변경은 작업 파일을 보존하면서 인덱스에서 분리했다. 연결되는 HTML·스크립트·SCSS와 컴포넌트 이름 변경을 같은 커밋에 포함한다.
- `data.txt`는 파일을 유지한 채 `.gitignore`의 `/data.txt`로 추적 대상에서 제외했다.
- `artifacts/`의 실험 캡처는 기능 커밋에서 제외했다.

| 커밋 | 범위 |
| --- | --- |
| `f2c9f5b` | 메뉴 패널과 섹션 이동 |
| `bb4952d` | 슬라이더·상품 설명 전환·비네팅 |
| `5d9bd31` | About 스타일·서체·헤더 스크롤 동작 |

위 커밋은 현재 브랜치 main에 생성했으며 해당 작업에서 push하지 않았다.

## 9. 화살표를 main Grid 영역으로 이동

관련 파일: [페이지 마크업](../src/pages/index.html), [페이지 스타일](../src/scss/pages/_home.scss), [슬라이더 스타일](../src/scss/components/_splide.scss).

문제는 화살표 wrapper에 `grid-area: shop`을 지정해도 바깥 main의 shop 영역으로 이동하지 않는 것이었다. wrapper는 별도의 Grid인 `.splide` 안에 있었다. 중간 컨테이너에 `display: contents`를 적용해도 가장 가까운 Grid는 여전히 `.splide`이므로 main의 영역 이름을 참조하지 못한다.

해결은 화살표 컨테이너를 `.c-main`의 직접 자식으로 옮기는 것이었다.

```text
.c-main
├─ .splide
├─ .c-splide__arrows
├─ .c-shop
└─ .c-about
```

- 불필요한 화살표 wrapper와 실험용 `display: contents`를 제거했다.
- 모바일·태블릿에서는 main을 한 열 Grid로 만들고 사진과 화살표를 같은 `splide` 영역에 겹친다. 화살표는 오른쪽 아래에 배치한다.
- 데스크톱에서는 화살표를 `shop` 영역의 왼쪽 아래에 배치한다. `z-index: 1`로 겹치는 콘텐츠 위에 표시한다.
- 버튼 그룹에는 `flex-wrap: nowrap`을 적용해 이전·다음 버튼이 줄바꿈되지 않게 한다.
- main의 데스크톱 열은 `repeat(12, minmax(0, 1fr))`로 명시해 12칸의 이름 있는 영역과 맞췄다. 첫 행은 사진 7칸·설명 5칸, 둘째 행은 About 영역이다.
- 버튼 ID를 유지해 기존 `splide.go('<')`, `splide.go('>')` 이벤트 연결을 유지했다.

검증 시 Grid 영역 경계와 실제 콘텐츠 박스를 구분해야 한다. `.c-shop`은 세로 중앙에 놓이므로 그 요소의 하단이 shop Grid 영역의 하단과 일치하지 않는다. 처음에는 콘텐츠 박스를 기준으로 검사해 실패했고, 실제 행·열 경계로 다시 측정했다.

**검증 완료 — 구조 변경 당시:** Chrome 헤드리스, 높이 900px·너비 375/768/1023px에서 사진 오른쪽 아래 배치, 1024/1440px에서 shop 영역 왼쪽 아래 배치와 다음 버튼 동작을 확인했다. 이후 별도로 추가한 데스크톱 이미지 비율·About 배치까지 모두 검증한 결과로 확대 해석하지 않는다.

## 10. 넓은 화면에서 fixed 헤더 정렬

헤더가 `left: 64px`로 화면에 고정된 반면 main은 최대 너비 1440px로 중앙 정렬되어 있었다. 화면이 더 넓어지면 main만 안쪽으로 이동해 헤더와 본문의 기준이 달라졌다.

데스크톱 inset을 다음처럼 변경했다.

```scss
inset: 64px auto auto calc(max(0px, (100% - 1440px) / 2) + 64px);
```

- `(100% - 1440px) / 2`는 화면이 main보다 넓을 때 생기는 왼쪽 여백이다.
- `max(0px, ...)`는 1440px 이하에서 음수 여백이 생기지 않게 한다.
- 여기에 64px을 더해 main 왼쪽 경계에서 일정하게 떨어지도록 한다.
- 여기서 백분율은 fixed 요소의 containing block을 기준으로 한다. 조상에 transform 등을 추가해 기준이 바뀌면 재검증해야 한다.
- main의 최대 너비를 변경하면 헤더 계산식의 1440px도 함께 갱신해야 한다.

**검증 완료 — 수정 당시:** Chrome 헤드리스, 높이 900px·너비 1024/1440/1500/1920/2560px에서 main 왼쪽 경계와 헤더 왼쪽 사이가 64px이며 헤더가 main 너비 안에 있음을 측정했다. 1920px에서는 main 왼쪽 240px·헤더 왼쪽 304px, 2560px에서는 각각 560px·624px이었다.

브라우저 검증은 최신 HTML·컴파일한 CSS를 요청 가로채기로 제공해 수행했다. dist를 수정하거나 삭제하는 빌드는 실행하지 않았다. Firefox, 확대, 수동 키보드 탐색을 포함한 전체 UI 검증은 미검증이다.

## 11. 접근성 개선 1차: 열린 메뉴의 스크롤 숨김 방지

관련 파일: [헤더 스크롤 처리](../src/js/main.js).

### 문제와 재현 조건

모바일 메뉴는 열릴 때 본문을 inert로 설정한다. 기존 스크롤 처리는 이 상태와 무관하게 scrollY가 100px을 넘으면 헤더에 u-hidden을 추가했다. 메뉴도 헤더 내부에 있으므로 함께 display: none으로 숨겨졌지만, 메뉴 열림 상태와 본문의 inert는 유지되어 메뉴와 본문을 조작할 수 없게 됐다. Chrome에서 메뉴를 열고 180px 아래로 스크롤하여 재현했다.

### 수정 내용

- 스크롤 숨김 조건을 `scrollY > 100 && !menuOpen && !focusInsideHeader`로 변경했다.
- 메뉴가 열려 있거나 헤더 내부에 키보드 포커스가 있으면 헤더를 표시한다. 포커스된 컨트롤이 스크롤 때문에 사라지는 상황도 함께 방지한다.
- 헤더가 없는 페이지에서 스크롤 처리를 실행해도 오류가 나지 않도록 확인 후 종료한다.
- 수정 위치에 `접근성 수정` 주석으로 원인과 보호 조건을 남겼다.
- 메뉴의 기존 닫기·Escape·분기점 전환 동작은 유지한다. 본문 inert는 메뉴를 정상적으로 닫는 경로에서 해제한다.

### 검증 결과

**검증 완료 — 이번 수정:** 최신 HTML·JavaScript·메모리에서 컴파일한 CSS를 Chrome 헤드리스에 제공했다. dist 수정·삭제 없이 실행했고 외부 웹폰트는 차단했다.

- 375×812, 667×375, 1023×900: 메뉴를 열고 180px 스크롤해도 메뉴가 표시되고, 닫기 버튼 실행 후 본문의 inert가 해제되며 열기 버튼으로 포커스가 복원됨.
- 375×812: 스크롤 후 Escape로 닫아도 inert 해제됨.
- 열린 메뉴를 스크롤한 상태에서 1024×900으로 전환: inert 해제됨.
- 1024×900: 내비게이션 링크에 포커스한 상태에서는 스크롤해도 헤더 표시 유지.
- 헤더 밖에 포커스가 있는 일반 상황: 100px 초과 시 헤더 숨김, 페이지 맨 위로 복귀하면 다시 표시.
- 위 시나리오에서 페이지 JavaScript 오류 없음. JavaScript 문법 검사와 공백 검사 통과.

**미검증:** Firefox, 스크린 리더, 실제 터치 기기 및 전체 수동 접근성 검증.

이번 단계는 메뉴 접근 불가 문제만 수정했다. 본문 대비, 확대 시 겹침, 로고 이름, 목적지 없는 링크·동작 없는 버튼 등 나머지 발견 사항은 별도 단계에서 처리한다.

## 12. 접근성 개선 2차: 본문 텍스트 색 대비

관련 파일: [색상 변수](../src/scss/abstracts/_variables.scss), [본문 스타일](../src/scss/pages/_home.scss).

### 문제와 수정

상품 설명과 About 설명은 흰 배경에 #A0A0A0을 사용해 대비가 약 2.61:1이었다. 일반 크기 텍스트의 WCAG AA 기준 4.5:1을 충족하도록 본문 전용 변수 `$color-body-text: #707070`을 추가하고 두 설명 스타일에 적용했다. 수정 이유는 변수 선언 위에 `접근성 수정` 주석으로 남겼다.

기존 `$grey-500` 팔레트 값은 유지했다. #707070과 흰색의 대비는 약 4.95:1이며, 이 판정은 해당 전경·배경 조합을 대상으로 한다. 모든 텍스트나 상호작용 상태의 대비 통과를 의미하지 않는다.

### 검증 결과

- **검증 완료:** 상대 휘도 공식으로 변경 전 2.61498:1, 변경 후 4.95214:1을 계산했다.
- **검증 완료:** Chrome 헤드리스, 높이 900px·너비 375/1024/1440px에서 각 3개 슬라이드를 전환하며 상품 설명과 About 설명의 computed color가 rgb(112, 112, 112), body 배경이 rgb(255, 255, 255)임을 확인했다.
- **검증 완료:** SCSS 출력 파일 없는 컴파일, 공백 검사. 최신 소스를 메모리에서 제공했고 dist는 수정하거나 삭제하지 않았다. 외부 웹폰트는 차단했으며 대비 판정은 글꼴 렌더링 대신 색상값을 기준으로 했다.
- **미검증:** Firefox, 실제 기기 시각 검토, 사진 위 텍스트·아이콘 및 전체 인터랙션 상태의 대비.

메뉴 접근 불가와 본문 대비 문제는 각각 1·2차에서 수정했다. 다음 단계는 확대 시 콘텐츠 겹침과 가로 넘침 개선이다.

## 13. 접근성 개선 3차: 확대 시 겹침과 가로 넘침

관련 파일: [페이지 스타일](../src/scss/pages/_home.scss).

### 원인과 수정

- 고정 Grid 행 534px·266px은 확대된 본문을 수용하지 못했다. `minmax(534px, auto) minmax(266px, auto)`로 최소 디자인 높이를 유지하면서 콘텐츠에 따라 늘리도록 했다.
- 같은 shop 영역에 겹치는 슬라이더 버튼을 위해 상품 영역 하단 공간을 확보했다.
- Grid 자식에는 `min-inline-size: 0`을 적용했다. 상품 영역은 `box-sizing: border-box`, 너비 100%, 긴 단어 줄바꿈을 사용해 l-center의 content-box와 내용 최소 너비로 인한 넘침을 방지했다.
- Shop now의 고정 너비 기반 margin 계산을 Flex gap으로 대체하고 텍스트 span의 최소 너비를 해제했다. 화살표는 축소되지 않게 했다.
- About 이미지는 고정 flex-basis 대신 비율로 공간을 나누고, 본문은 모든 화면에서 border-box·너비 100%·줄바꿈을 적용했다.
- 제목·설명의 줄 높이는 글자 크기에 따라 늘어나는 단위 없는 값으로 조정했다.
- 사용자가 직접 변경한 rem 간격, em 자간, 메뉴 height: auto와 위아래 2.9375rem padding을 유지했다. 메뉴에는 max-block-size: 100dvh를 추가하고 데스크톱에서는 제한을 해제했다.
- 해당 위치에 접근성 수정 주석을 남겼다. 공통 l-center 유틸리티 자체는 변경하지 않았다.

이 단계는 처음에 일부 수정만 적용된 뒤 추가 쓰기 명령이 거부되어 중단됐고, 사용자의 계속 진행 요청에 따라 남은 너비·줄바꿈 수정을 완료했다.

### 검증 결과와 한계

**검증 완료 — 재개 후 최신 소스:** Chrome 헤드리스에 HTML·JavaScript·컴파일 CSS를 메모리로 제공했다. vendor CSS도 text/css로 제공했으며 외부 웹폰트는 차단했다. 앞선 중간 검사에서는 vendor CSS 응답 형식이 잘못되어 레이아웃 수치가 왜곡됐으므로 그 수치를 최종 근거로 사용하지 않는다.

- 높이 900px, 너비 320/375/720/768/1023/1024/1440px에서 기본·루트 글꼴 200%·본문 글자만 200% 조건을 각각 검사했다.
- 본문 글자만 확대 검사는 텍스트 노드가 있는 요소의 computed font-size를 두 배로 지정한 시뮬레이션이다. 루트 확대와 별도로 구분했다.
- 총 63개 조합(3조건 × 7너비 × 3슬라이드)에서 문서 가로 넘침, Shop/About 경계 침범, 데스크톱 설명과 슬라이더 버튼 겹침, About 본문의 footer 경계 침범이 없음을 측정했다.
- 320×568 및 667×375에서 루트 글꼴 200%로 메뉴를 열어 높이가 viewport 이내임을 확인했다. 마지막 메뉴 링크를 포커스했을 때 화면 안에 있었고 Escape 후 본문 inert가 해제됐다.
- 검사한 메뉴 높이는 각각 448px·238px로 내부 스크롤이 필요한 조건은 아니었다. 실제로 메뉴가 viewport보다 길어지는 조건의 내부 스크롤은 별도 검증이 필요하다.
- SCSS 컴파일·공백 검사 완료. dist를 수정하거나 삭제하지 않았다.

**미검증:** 브라우저 UI의 실제 200% 확대, Firefox, 실제 웹폰트 기준 시각 검토, 스크린 리더 및 모든 포커스·고대비 상태. 720px 검사는 좁은 CSS viewport 확인이며 실제 브라우저 확대 조작과 동일한 검증으로 취급하지 않는다.

## 14. 접근성 개선 4차: CSS 마스크 로고의 이름 제공

관련 파일: [헤더 마크업](../src/pages/index.html).

기존 로고는 빈 span에 CSS 마스크로 표시되어 브랜드명이 보조 기술에 전달되지 않았다. 기존 마스크 표현을 유지하면서 `role="img"`와 `aria-label="room"`을 추가했다. 링크나 버튼 역할은 부여하지 않았으며, HTML 바로 위에 접근성 수정 주석을 남겼다.

- **검증 완료:** Chrome 헤드리스 375×900·1440×900에서 역할·이름 조회가 정확히 하나의 이미지를 찾고 접근성 스냅샷이 `img "room"`을 반환했다.
- **검증 완료:** 기존 크기 62×14 CSS px 유지, tabIndex -1로 새 Tab 정지점이 추가되지 않음. 최신 소스·컴파일 CSS를 메모리로 제공하고 dist는 변경하지 않았다.
- **검증 완료:** 공백 검사.
- **미검증:** 실제 스크린 리더 읽기, Firefox, 고대비 모드에서 CSS 마스크 표시.

다음 단계는 Home·Contact의 실제 목적지와 Shop now 동작을 결정하는 것이다. 목적지를 임의로 만들지 말고 placeholder 여부와 원하는 이동·동작을 확인해야 한다.

## 15. 접근성 개선 5차: Home 링크의 실제 목적지

관련 파일: [페이지 마크업](../src/pages/index.html).

Home 링크의 #home 대상이 없었던 문제를 해결하기 위해 body에 고유한 id="home"을 추가했다. HTML 주석에 이유를 남겼다. fixed 헤더는 스크롤 목적지로 사용하지 않았다.

- **검증 완료:** Chrome 헤드리스 375×812에서 메뉴를 열고 180px 스크롤한 뒤 Home 링크를 클릭했다. 메뉴 닫힘(aria-expanded=false), 본문 inert 해제, hash=#home, scrollY=0, home ID 1개를 확인했다.
- **미검증:** Firefox, 실제 스크린 리더와 해당 링크의 전체 입력 방식.
- **사용자 결정 — 수정 범위에서 제외:** Contact·Shop now는 당분간 placeholder로 유지한다. 실제 목적지·동작은 미구현 상태이며 접근성 문제가 해결된 것으로 기록하지 않는다. 이후 점검에서는 의도적 미구현으로 구분하고 목적지를 반복해서 요청하지 않는다. Home 수정만 완료했다.

## 16. 접근성 개선 6차: 동작 줄이기 전환 규칙 보완

관련 파일: [헤더 스타일](../src/scss/pages/_home.scss), [메뉴 스타일](../src/scss/components/_nav-panel.scss).

- 헤더의 opacity·transform 전환에 prefers-reduced-motion: reduce 시 transition: none을 추가했다.
- 기존 상품 화살표의 margin 전환은 확대 대응 때 제거되어 별도 수정이 필요하지 않았다.
- 검증 중 메뉴 열림 선택자 `.c-nav-panel.is-open .c-nav-panel__inner`가 기존 reduce 규칙보다 우선해 실제 열기 전환이 실행되는 문제를 발견했다. reduce 미디어 쿼리 안에도 같은 우선순위의 열림 선택자를 추가해 해제했다.
- 두 변경 위치에 접근성 수정 주석을 남겼다.

**검증 완료:** Chrome 헤드리스 375×900·1440×900, no-preference·reduce 네 조합을 검사했다. 일반 설정의 헤더 전환은 0.3초, reduce는 0초였다. 모바일 메뉴를 실제로 연 뒤 일반 0.3초·reduce 0초를 확인했고 reduce 메뉴의 활성 애니메이션은 0개였다. reduce 상태에서 다음 버튼 실행 후 사진 트랙·새 설명의 활성 애니메이션은 0개이며 새 설명이 즉시 표시됐다. 일반 설정에서도 설명 전환이 정상 완료됐다.

최신 소스와 메모리 컴파일 CSS로 검사했으며 dist는 변경하지 않았다. 외부 웹폰트는 차단했다. SCSS 컴파일·공백 검사 완료. 실제 OS 설정 변경·스크린 리더·Firefox는 미검증이다. 이 검증만으로 모든 모션 관련 접근성 기준을 충족한다고 보장하지 않는다.

## 17. 후속 작업 보류

사용자 요청으로 hover·focus 상태 개선은 보류했다. 해당 단계에서는 소스 확인 명령이 거부되어 코드 변경을 수행하지 않았다. 현재 완료된 접근성 수정과 개발 기록을 먼저 커밋하며, Contact·Shop now는 기존 결정대로 placeholder를 유지한다. 별도로 삭제된 Figma 문서 4개와 sample.html은 접근성 커밋에 포함하지 않는다.

## 18. 메뉴 배경 오버레이

메뉴가 열리면 헤더의 ::before를 position: fixed와 inset: 0으로 화면 전체에 표시하고 rgba(0, 0, 0, 0.5)를 적용했다. :has([data-nav-panel].is-open)으로 열림 상태에 연동하며 패널은 z-index: 1로 오버레이 위에 표시한다. 닫힘·데스크톱에서는 오버레이를 숨긴다. 배경 클릭으로 닫는 동작은 추가하지 않았다.

검증 완료: Chrome 헤드리스 375×812·667×375·1023×900에서 오버레이의 computed 크기가 viewport와 일치하고 배경색의 알파가 0.5임을 확인했다. 닫기 버튼·Escape로 숨김, 1440px 데스크톱 전환 시 숨김을 확인했다. SCSS 컴파일·공백 검사 완료. 최신 소스를 메모리로 제공했으며 dist는 변경하지 않았다. Firefox와 실제 기기 시각 검토는 미검증이다.

## 19. hover・focus 상태 개선 재개

관련 파일: [페이지 스타일](../src/scss/pages/_home.scss), [슬라이더 스타일](../src/scss/components/_splide.scss).

사용자 요청으로 보류했던 인터랙션 개선을 재개했다. Contact·Shop now는 placeholder를 유지하며 동작·목적지는 추가하지 않았다.

- 메뉴 열기: hover·focus-visible에 반투명 검정 배경을 표시한다.
- 메뉴 닫기: 밝은 회색 배경을 표시하고 활성 상태 SVG path의 낮은 opacity를 해제한다.
- 메뉴 링크: 모바일·데스크톱에서 hover·focus-visible에 밑줄을 표시한다. 기존 데스크톱 짧은 밑줄도 focus-visible에 제공한다.
- 이전·다음: hover 배경을 #444로 바꾸고 기존 흰색 안쪽 포커스 윤곽선을 유지한다.
- Shop now: 텍스트와 화살표 색을 #444로 맞추고 밑줄을 표시한다.
- 푸터 링크: 검정색과 두꺼운 밑줄로 피드백을 제공한다. 스킵 링크에는 hover 시 이중 밑줄을 제공한다.
- 메뉴·Shop now·푸터의 focus-visible에는 검정 윤곽선과 흰색 바깥 표시를 함께 제공한다. 초점 표시를 위해 움직이는 애니메이션은 추가하지 않았다.
- 변경 위치에 인터랙션 개선 주석을 추가했다.

**검증 완료:** 최신 소스·메모리 컴파일 CSS를 제공한 Chrome 헤드리스 375×900에서 스킵 링크, 열기·닫기 버튼, 메뉴 링크 4개, 이전·다음, 상품 버튼 3개, 푸터 링크 2개의 hover·키보드 focus-visible computed style을 검사했다. 1440×900에서도 메뉴 링크 4개의 hover·focus-visible을 확인했다. 메뉴 Enter 열기·Escape 닫기와 다음 버튼의 Enter·Space 실행 후 상품 설명 변경을 확인했다. SCSS 컴파일·공백 검사 완료.

첫 자동 검사는 포커스된 스킵 링크가 메뉴 버튼의 포인터 입력을 가려 중단됐다. 스킵 링크 검사 후 포커스를 옮겨 다시 검사했고 위 결과를 얻었다. 실제 포인터·키보드 혼용 시 스킵 링크 위치의 겹침은 별도 검토할 수 있다.

**미검증:** Firefox, 실제 웹폰트·기기 기준 시각 검토, 스크린 리더, 고대비 모드, 모든 배경에서의 포커스 표시 대비·가려짐 수동 검증. 브라우저 스타일 검사만으로 완전한 접근성 준수를 보장하지 않는다.

## 20. 섹션별 SCSS 컴포넌트 분리

_home.scss에 모여 있던 섹션 스타일을 components로 분리했다.

| 파일 | 역할 |
| --- | --- |
| [header](../src/scss/components/_header.scss) | 헤더, 홈페이지 메뉴 외형·설정, 오버레이, 메뉴 hover |
| [splide](../src/scss/components/_splide.scss) | 기존 슬라이더 스타일과 슬라이더 컨테이너 |
| [shop](../src/scss/components/_shop.scss) | 상품 설명과 Shop now 상태 |

| [skip-link](../src/scss/components/_skip-link.scss) | 기존 스킵 링크와 해당 hover |
| [home](../src/scss/pages/_home.scss) | body와 페이지 전체 Grid·섹션 배치 |

메뉴 열림·닫힘의 공통 구조는 기존 _nav-panel.scss에 유지했다. style.scss에 새 모듈을 연결했으며 유틸리티는 마지막에 로드한다. 기존 주석과 스타일 값을 유지했고 사용자 작업 중인 HTML include 파일은 수정하지 않았다. 초기 분리에서는 푸터 기본 인라인 스타일을 유지했고, 최종 검토에서 _attribution.scss로 이동했다. 이전 기록의 home.scss 링크는 수정 당시 위치이며, 현재 섹션 스타일은 위 파일에서 확인한다.

**검증 완료:** 분리 전후 컴파일 CSS를 PostCSS로 분석해 151개 선택자·미디어 조건 그룹의 속성값과 동일 그룹 내 선언 순서가 일치함을 확인했다. 서로 다른 선택자 사이의 전체 캐스케이드 순서까지 동일하다는 의미는 아니다.

HTML include를 gulp-file-include로 메모리에서 처리하고 최신 CSS를 제공한 Chrome 헤드리스 375/768/1023/1024/1440×900에서 Shop·About 존재, 모바일 메뉴 열기·Escape 닫기·오버레이, 다음 버튼의 설명 전환, 문서 가로 넘침 없음을 확인했다. 페이지 JavaScript 오류 없음, SCSS 컴파일·공백 검사 통과. dist를 수정·삭제하는 명령은 실행하지 않았다. Firefox·전체 시각 비교·확대·모든 상태 재검증은 미검증이다.

## 21. 분리된 컴포넌트의 Storybook

src/stories에 Header·Splide·Shop·About·Attribution·SkipLink·InteractionStates 스토리를 추가했다. 기존 NavPanel 스토리 2개는 유지했다. 새 예시 16개를 포함해 총 18개다.

- 실제 index.html의 헤더·푸터·화살표와 분리된 sections HTML을 Vite raw import로 재사용한다.
- Header는 실제 initNavPanel을 연결하며 기본·열림 예시를 제공한다. 모바일 폭에서 열림·오버레이를, 데스크톱에서 펼쳐진 메뉴를 확인한다.
- Splide는 기존 vendor 스크립트와 스타일을 사용한다. 시작 사진·속도·설명 표시 Controls 및 기본·설명 연동·세 번째 사진·즉시 전환 예시를 제공한다. 설명 선택 상태만 동기화하며 홈페이지의 설명 페이드 애니메이션은 복제하지 않았다.
- Shop은 세 상품 예시와 선택 Controls, About은 세로·페이지 행 배치 예시를 제공한다.
- SkipLink와 InteractionStates는 기본·포커스 예시를 제공한다. hover는 실제 포인터를 올리고 키보드 포커스는 Tab으로 확인한다.
- 커스텀 데모 요소의 연결·해제 콜백으로 메뉴·슬라이더 인스턴스와 이벤트·inert 상태를 정리한다.
- Docs 예시는 iframe으로 분리해 고정 위치와 중복 ID의 간섭을 줄인다. 단독 Canvas의 화면 너비를 변경해 1024px 전후를 확인할 수 있다.
- Contact·Shop now는 기존 결정대로 placeholder다. 헤더 스토리의 앵커는 Storybook을 벗어나지 않도록 예시 내부 해시로 변환한다.

Storybook 설정에서 존재하지 않는 src/fonts 정적 폴더를 제거했다. 원본 이미지·vendor 자산을 staticDirs로 제공하고 preview-head에 홈페이지와 같은 Google Fonts 링크 및 Splide 원본 스크립트를 연결했다. UMD vendor를 Vite 모듈로 직접 import하면 생성자가 등록되지 않아 원본 script 로딩으로 변경했다. preview.css는 Storybook의 로고 경로를 보완한다. 푸터 기본 스타일은 최종 검토에서 attribution 컴포넌트에 통합해 preview 중복을 제거했다.

실행: `npm run storybook`. 설정 변경이 있으므로 기존 개발 서버가 있다면 재시작한다. 빌드는 `npm run build-storybook -- --output-dir .git/storybook-components-review --disable-telemetry`로 수행했다. 이 출력은 임시 검증용이며 dist를 수정·삭제하지 않는다.

**검증 완료:** 스토리 JavaScript 문법 검사, Storybook 정적 빌드, SCSS 컴파일. 초기 전체 공백 검사에서는 style.scss의 파일 끝 빈 줄을 확인했고 최종 검토에서 정리했다. Chrome 헤드리스 375×900에서 18개 스토리 렌더링, 메뉴 Escape·inert 해제, 데모 제거 시 정리, 스킵 링크 Focused 예시, 다음 버튼의 설명 연동을 검사했다. 1440×900에서 헤더 표시와 슬라이더 실행을 검사했다. 페이지 JavaScript 오류·자산 404 없음. 외부 웹폰트 요청은 차단했다.

빌드 경고: MDX 파일 없음, 정적 logo.svg의 런타임 경로 해결, 큰 번들 청크. 로고는 실제 브라우저에서 404가 없음을 확인했다. Firefox·실제 웹폰트 렌더링·모든 Controls 조합·Docs 전체 수동 시각 검토는 미검증이다. 배포·커밋은 수행하지 않았다.

## 22. 컴포넌트 분리·Storybook 최종 검토

푸터 기본 글꼴·색상과 사용자 추가 상단 여백 10px을 attribution 컴포넌트로 통합하고 Storybook preview 중복 선언을 제거했다. 이동 전후 컴파일된 선택자별 선언이 일치함을 확인했다. HTML include 처리·스토리 JavaScript 문법·SCSS 컴파일·전체 공백 검사와 최종 Storybook 빌드를 완료했다. 최종 빌드의 18개 스토리 렌더링 및 설명 연동 슬라이더를 Chrome에서 재검사했고 페이지 JavaScript 오류와 자산 404가 없었다. 외부 웹폰트는 차단했다. Firefox·전체 시각 검토는 미검증이다.

[홈페이지 캡처](../screenshot.jpg)를 확인해 문서용 이미지로 포함한다. 사진은 실제 UI 캡처이며 모든 최신 상태의 정확성을 보장하는 회귀 기준은 아니다. 기존 chromatic.yml에는 변경이 없으며 push나 Chromatic 배포는 실행하지 않았다.
